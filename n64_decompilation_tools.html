1. The most important tools

The core of a matching decompilation workflow is Splat, spimdisasm, Ghidra, m2c, decomp.me, asm-differ, and a suitable original compiler toolchain. REA adds agent-assisted investigation; it does not replace ROM-specific tooling.

2. Six tools to learn first

01

Splat — project extraction

Splits ROMs into sections such as assembly, code, initialized and uninitialized data, and supported asset types. Uses a YAML configuration describing the game's layout.

Use when: Starting and organizing a decompilation project.
02

spimdisasm — disassembly

Produces human-readable MIPS assembly and helps identify symbols, references, code, rodata, data, and BSS; commonly used by Splat.

Use when: Mapping functions, addresses, and references.
03

Ghidra + N64LoaderWV

Explore function graphs, cross-references, pseudo-C and memory usage. The N64 loader helps handle ROM byte order and memory layout.

Use when: Understanding an unfamiliar function's behavior.
04

m2c — C reconstruction

Converts MIPS assembly to approximate C with conditionals, loops, pointers and candidate types. Output is a starting point, not automatically matching source.

Use when: Reconstructing one assembly function in C.
05

asm-differ — assembly matching

Shows differences between original and recompiled assembly, helping pinpoint register choices, instruction ordering and compiler optimization details.

Use when: Iterating toward instruction-for-instruction matches.
06

IDO Static Recomp — compiler fidelity

Provides static recompilations of SGI IDO 5.3 and 7.1 compiler components for modern systems. Exact compiler choice varies by game.

Use when: Targeting a game originally compiled with IDO.

3. Added tool: REA — Reverse Engineer Anything

AI-assisted reverse engineering

morluto/rea on GitHub ↗

REA is an MCP-based reverse-engineering toolkit connecting AI agents to tools that analyze native binaries, application code and runtime behavior. For native analysis, it can work with existing Ghidra, Hopper or IDA installations to surface pseudocode, assembly, symbols, call references and evidence-backed findings.

Where it fits for Nintendo 64: useful for agent-guided code exploration and understanding binary behavior when a compatible native analysis provider has correctly loaded the ROM. Treat N64-specific loading, memory mapping, asset extraction and matching builds as separate steps handled by tools such as Splat, N64LoaderWV and asm-differ.

REA is a companion for analysis, not a verified one-click N64 ROM decompiler or a replacement for matching-toolchain validation.

Requirements: Node.js 22.19+, 24.11+, or 26+ and npm, according to the repository. Native analysis also requires a supported backend.

Setup command from the REA project:

npx rea-agents setup

Follow the setup prompts, review the changes, and restart your agent. Official docs: rea.tools. Verify platform/provider support for your N64 analysis setup.

6. Progress tracking — inspired by Brally

Brally (Boss Rally / Top Gear Rally) tracks reconstructed functions using two distinct milestones, reports completion by original code bytes, and generates a per-function progress treemap. This prevents lots of tiny matched functions from hiding large unfinished ones.

Brally snapshot numbers are fixed historical reference values, not live readings. Its source repository provides tools/brally/progressbar.py, tools/brally/progressmap.py, and tools/tgrally/n64map.py to regenerate tracking from the project tree. See its current status and methodology ↗

Your own offline, editable decompilation tracker

Paste a CSV inventory containing area,function,bytes,tier. The file calculates M1 (T3 + T4) and M2 (T4) by eligible bytes, plus function counts, and creates a function-sized visual map grouped by area. Tiers: T1 unstarted, T2 in progress, T3 behavior validated, T4 byte-exact; excluded means library/SDK or other out-of-scope code. Example data is fictional, not from Brally or an actual ROM.

Data stays in this browser and can be exported; this is an illustrative dashboard, not a direct import of Brally's source-code analysis or a substitute for compiler/build verification.

How to implement this in a real project

  1. Generate an exhaustive function inventory from Splat/spimdisasm or your binary analysis. Keep a stable address, section/module, original instruction-byte count and tier for every function.
  2. Maintain a strict definition of T4: compiled instructions and relocation-dependent addresses match the target. Treat a working but nonmatching function as T3 only after suitable behavior validation.
  3. Compute M1 = (T3 + T4 eligible bytes) / all eligible bytes and M2 = T4 eligible bytes / all eligible bytes. Also display the function-count ratio separately.
  4. Generate a color-coded per-function map, organized by module; flag unclassified regions and missing coverage. Exclude SDK/library code explicitly rather than silently dropping it.
  5. Regenerate the metrics and map from inventory or build results in CI to prevent stale dashboards. Use the final assembled-image comparison to catch overlaps and other binary mismatches.

Useful Brally references: progressbar.py · progressmap.py · n64map.py.

7. Starter setup (Ubuntu / WSL2)

Install system development packages, make an isolated Python environment, and obtain the core repositories. Exact per-game setup requires a matching ROM revision, section map and compiler configuration.

sudo apt update
sudo apt install \
  git make build-essential \
  python3 python3-pip python3-venv \
  binutils-mips-linux-gnu

python3 -m venv .venv
source .venv/bin/activate

pip install 'splat64[mips]' spimdisasm rabbitizer

git clone https://github.com/matt-kempster/m2c.git
git clone https://github.com/simonlindholm/asm-differ.git
git clone https://github.com/decompals/ido-static-recomp.git

For REA, install a supported Node.js/npm version, configure a compatible native analysis backend, then run:

npx rea-agents setup
Not every N64 game used IDO. The compiler, linker scripts, assets, symbols and build recipes must be tailored to the particular game. REA installation is optional.

For examples, explore the Super Mario 64 decompilation and Ocarina of Time decompilation repositories.

8. Choose tools for your goal

What do you want to accomplish?

Recommended: Splat → m2c → target compiler → asm-differ → decomp-permuter.

Start with one function at a time. Use Ghidra and optionally REA to investigate unfamiliar logic.

9. Final recommendation

Learn Splat, Ghidra, m2c and asm-differ first. Together, these cover the main cycle of extracting, understanding, reconstructing and comparing game code. Add a compatible original compiler when attempting exact matches, REA for agent-assisted investigation, and game-specific extraction tools when assets are the priority.
